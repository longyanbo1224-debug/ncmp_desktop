# ncmp v1.2.5

一次执行评满 20 首，修正分数口径导致的曲线 / 颜色问题，并把批注改为默认关闭。

## 双端共同

### 修复

- **点一次只评 15 首，要再点一次才到 20**：额外任务接口是分批返回的，
  新的一天先返回 15 条（其中混着基础 5 首），基础评完后才放出剩下的 5 首额外。
  以前额外阶段沿用执行前预取的旧清单，评完首批就结束。现在基础评完后会重新拉一次额外清单，
  并按「额外每日 15 首额度」继续补跑，一次执行就能评满 **5 基础 + 15 额外 = 20 首**。
- **口味曲线只累计当天、昨天的不见了**：服务端有时把分数返回成 `4.0` 这种浮点数，
  旧代码 `int("4.0")` 失败后把它当成「没有分数」，所以只有本地回调写入整数分数的当天记录
  进了曲线。现在分数统一归一化成 1–5 的整档，读取旧账本时也会归一化，
  已经落盘的 `"4.0"` 历史记录会重新计入曲线，不用重跑。
- **重新打开后曲目分数变红 / 显示 `4.0⁄5`**：同一原因。现在解析、账本、曲目表、显示层
  都走同一条归一化规则，`4.0` 会正确显示为 4 分并走对应档位颜色。
- **第一首点下开始就立刻提交**：现在与上游 ncmp 一致，**每次真实评分请求前都等待**
  （含第一首），默认 15–20 秒；账本命中 / 跳过已评过的歌不等待、不发请求。
- **缺 `id` 的作品串号**：额外阶段去重时，缺 id 的作品曾共用 `"None"` 一个键，
  评上第一首后其余缺 id 的歌都会被跳过。现在优先用 id，缺 id 时退到歌名，
  真正无 id 无名的作品不会互相当成同一首。
- **「今日额外额度已用完」按今日完成计**：服务端返回 405「今日没有更多可评定歌曲」时，
  没轮到的额外曲目按今日完成显示（和 1.2.4 的历史展示一致），摘要注明「今日额外额度已用完」；
  普通取消 / 单首失败留下的「跳过」**不会**被算成完成。
- **本地额度缓存：重跑不再等 15 秒探针**：第一次收到「今日没有更多」后，按
  「账号 + 日期 + taskId」记在本机；同一天同一任务再点执行时**先查本地**，命中就直接
  跳过额外阶段，不再等待 15–20 秒、不再发评分请求。换天 / 换任务自动失效。
- **本地账本 / 历史已评满时同样直接跳过**：本地账本已经确认收下「基础 + 额外上限」这么多首，
  或者本机今日曲目记录里已经有这么多首 `submitted` 时，即使服务端清单还标着待评，
  也直接按今日已评满处理，不再发评分请求（仍保留一次只读清单拉取用于显示完整曲目）。
- **重复执行按本地历史展示**：本机记录为 `submitted` 的曲目直接显示为已完成
  （即使没有分数，也按 1.2.4 的历史口径处理）；取消 / 失败留下的「跳过」保持
  「跳过」，不会被历史里的其他曲目带成完成。
- **同名不同作品只显示 19 首**：曲目表原来按歌名去重，额外清单里两首同名、不同歌手的
  作品会被合并成一行，20 首变成 19 首。现在内部按「歌名 + 歌手」区分，两首各占一行，
  进度 / 批注回调按待评行依次匹配。
- **补拉清单失败导致额外阶段整个失败**：重新拉取失败时沿用执行前的清单，
  不会因为一次临时网络错误让整轮额外任务失败。

### 改进

- 分数归一化收口到 `core/scoring.clean_score`：空串、`null`、`0` / `0.0`、
  `4.5`、`nan` / `inf` 都按「没有分数」处理，`4.0` / `5.0` 按整档处理。
- 首次启动时间不会因为迁移变长：批注默认关闭的一次性迁移只执行一次。

## 手机端

- **曲目表先 15 行、基础评完自动补到 20 行**：基础阶段结束后重新拉额外清单，
  同一次执行把曲目表补齐并继续评分，不需要再点「开始评分」。
  补拉的批次里如果出现已摆过的歌，会按「歌名 + 歌手」合并进已有行，
  曲目表不会先 15、评分中又涨到 25。
- **听歌记录上报失败不再谎报已提交**：以前上报失败后曲目会停在「待评」，
  成功收尾时又被当成「已提交」多算一首；现在标为「失败」，补跑轮仍会再试一次。
- **取消任务立即停止**：额外清单预取 / 重新拉取不再用 `runCatching` 吞掉
  `CancellationException`，取消后会立刻停在当前阶段。
- **查积分同样响应取消**：`getPartnerPoints()` 不再把取消当成普通异常吞掉。
- **旧记录分组更稳**：额外阶段重新摆清单时，会把曲目表里已有的基础行列进 `baseNames`，
  避免旧版本没有分组信息的记录被误归为额外后裁掉。
- **刷新后状态与桌面端一致**：本机记录为 submitted 时按已完成显示（即使没有分数），
  skipped / failed 按本机状态显示；本地额度缓存命中时直接跳过额外阶段。
- **本地额度缓存同样生效**：同一天同一 taskId 重跑时直接跳过额外阶段，不再等待、不再发请求。
- **批注默认关闭**：升级后第一次启动会把旧版本落盘的 `note_enabled=true` 一次性关掉；
  之后完全尊重用户在设置里手动打开并保存的选择。

## 桌面端

- **额外阶段重新拉清单**：基础任务评过后不再复用执行前的预取结果，
  而是重新请求额外清单；接口分批时也会继续补跑，直到评满额外 15 首额度。
- **批注默认关闭 + 一次迁移**：旧版本默认开启；升级后第一次启动把 `setting.json`
  里的 `note_enabled` 改成 `false`，之后以用户手动保存的设置为准。
  （GitHub Actions 环境会跳过这次迁移，避免全新 runner 反复改写配置。）
- **额外清单异常条目容错**：返回数据里混入非对象条目时直接忽略，不会让额外阶段中断。
- **基础任务剔除更严**：额外清单里 `id` 为 `null` 的作品也不会被误当成基础任务。
- **分数显示与统计统一**：旧账本里的 `4.0` / `3.0` 会按 4 分 / 3 分显示和统计，
  不再显示成 `4.0⁄5` 或因为转整数失败掉进红色低档。
- **额外任务「没有更多」不再打 ERROR**：405「今日没有更多可评定歌曲」现在按正常
  完成信号处理，日志只留一条 INFO，不再出现「评分异常 / 处理额外任务失败」，
  也不会再为此多查一次确认接口。

## 说明

- 服务端一次最多返回 15 条额外曲目，基础未评时会混入基础 5 首；因此**点下开始时仍可能先看到 15 行**，
  这是接口行为，不是丢歌。基础评完后会自动补齐到 20 行，同一次执行继续评完。
- 已经以**空分数**落盘的历史记录无法恢复（当时分数已经丢失）；仍保留 `4.0` 这类浮点分数的记录会自动恢复。
- 基础阶段单首网络异常仍会中止整轮（与上游一致）；额外阶段单首失败会跳过并在补跑轮重试。
- **云端执行不受本次改动影响**：云端仍由目标仓库里的 workflow 执行，触发 / 轮询 / 状态代码未改；
  本地额度缓存、历史跳过、首首等待等只作用于本地执行。批注「默认关闭」只在本地生效，
  GitHub Actions 环境保持旧的默认开启。
